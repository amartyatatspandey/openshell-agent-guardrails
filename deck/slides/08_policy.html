The whole policy: four decisions, all deny-by-default

1filesystem_policy: read_only: [/bin, /usr, /lib, /proc, /dev/urandom, /etc, /var/log] read_write: [/tmp, /dev/null] landlock: compatibility: hard_requirement 2process: run_as_user: "1000" run_as_group: "1000" 3network_policies: github_readonly: endpoints: - host: api.github.com port: 443 protocol: rest enforcement: enforce access: read-only binaries: [ /usr/bin/curl ] public_echo: # httpbin.org, same shape 4# provider demo-github, attached at create: GITHUB_TOKEN=FAKE_NOT_A_REAL_TOKEN
1

Landlock, and no silent downgrade

The agent sees a short read-only list and /tmp. hard_requirement means: if the kernel can't enforce Landlock, the sandbox doesn't start at all.

2

Never root

The workload runs as uid/gid 1000 from the first instruction.

3

Two hosts, read-only, curl only

Anything not listed is denied. read-only denies writes by method. The binary list means python3 to the same host is still a deny.

4

A credential that can't leak

The gateway keeps the value. The sandbox gets a placeholder that only resolves on the bound endpoint.

Proof design
The image plants /opt/company/prod.env (fake values) and runs chmod 0644, so it's world-readable. Unix permissions would allow the read. When it's denied, only Landlock could have done it. The demo proves the control, not an accident of chmod.
